    30→    30→## 1. What Is ScholarAI?
    31→    31→
    32→    32→ScholarAI is an **intelligent academic research assistant** — a full-stack web application that takes a natural-language research query (e.g. *"I need recent papers about blockchain in healthcare with more than 50 citations but no survey papers"*) and returns a curated, deduplicated, AI-ranked list of papers from **four major academic repositories simultaneously**.
    33→    33→
    34→    34→For every paper returned, the system can additionally produce a **structured AI analysis** — short summary, key contributions, advantages, limitations, future scope, and extracted keywords — so researchers can decide whether a paper is worth reading *before* they open it.
    35→    35→
    36→    36→### Core Promise
    37→    37→
    38→    38→| Instead of... | ScholarAI... |
    39→    39→|---|---|
    40→    40→| Searching one source at a time | Queries 4 academic APIs **in parallel** |
    41→    41→| Manual deduplication of cross-source results | Merges duplicates via **DOI + title similarity** |
    42→    42→| Sorting by date or citation only | Ranks with a **weighted relevance score (0–100)** |
    43→    43→| Reading the abstract to guess if it's relevant | Generates **AI insights** (summary, pros, cons) on demand |
    44→    44→| Manually formatting citations | Exports in **APA, MLA, BibTeX, Chicago** with one click |
    45→    45→| Losing track of papers across sessions | Saves papers, search history & favorites in a **persistent library** |
    46→    46→

    48→    48→
    49→    49→## 2. The Problem We Solve
    50→    50→
    51→    51→Researchers today face a fragmented discovery workflow:
    52→    52→
    53→    53→- **Source fragmentation** — relevant papers live across Semantic Scholar, arXiv, Crossref, PubMed, CORE, and dozens of publisher sites. Each has its own UI, search syntax, and metadata shape.
    54→    54→- **Duplicate noise** — the same paper appears on multiple sources with slightly different metadata (arXiv preprint → Crossref-published journal version → Semantic Scholar entry with citations).
    55→    55→- **No relevance ranking** — most sources sort by date or citation count, not by *semantic fit* to the researcher's actual question.
    56→    56→- **Shallow metadata** — abstracts alone rarely tell you whether a paper's contribution matters for *your* problem. You need analysis.
    57→    57→- **Manual citation drudgery** — copy-pasting BibTeX from one site, fixing author names, re-formatting to APA for a different submission.
    58→    58→- **No memory** — every search starts from scratch. There's no library, no history, no recommendations.
    59→    59→
    60→    60→ScholarAI eliminates all of these in a single integrated web app.

    64→    64→## 3. The Solution — End-to-End Pipeline
    65→    65→
    66→    66→When a user submits a query, ScholarAI runs a **9-step pipeline**:
    67→    67→
    68→    68→```
    69→    69→┌─────────────────────────────────────────────────────────────────────────┐
    70→    70→│                        USER SEARCH QUERY                                │
    71→    71→│  "I need recent papers about blockchain in healthcare with 50+          │
    72→    72→│   citations but no survey papers"                                       │
    73→    73→└──────────────────────────────────┬──────────────────────────────────────┘
    74→    74→                                   │
    75→    75→                                   ▼
    76→    76→┌─────────────────────────────────────────────────────────────────────────┐
    77→    77→│  STEP 1 — AI QUERY UNDERSTANDING                                        │
    78→    78→│  LLM parses the natural-language query into:                            │
    79→    79→│  { topic, intent, keywords, excludeKeywords, searchTerms, filters,      │
    80→    80→│    reasoning }                                                          │
    81→    81→│  Falls back to heuristic keyword extraction if the LLM fails.           │
    82→    82→└──────────────────────────────────┬──────────────────────────────────────┘
    83→    83→                                   │
    84→    84→                                   ▼
    85→    85→┌─────────────────────────────────────────────────────────────────────────┐
    86→    86→│  STEP 2 — PARALLEL MULTI-SOURCE SEARCH                                  │
    87→    87→│  The orchestrator fans out to 4 sources concurrently with a 12-second   │
    88→    88→│  per-source timeout. Each adapter normalizes its source's response      │
    89→    89→│  into a common AcademicPaper shape.                                     │
    90→    90→└──────────────────────────────────┬──────────────────────────────────────┘
    91→    91→                                   │
    92→    92→                                   ▼
    93→    93→┌─────────────────────────────────────────────────────────────────────────┐
    94→    94→│  STEP 3 — DATA NORMALIZATION                                            │
    95→    95→│  Each adapter (semantic-scholar.ts, arxiv.ts, crossref.ts, pubmed.ts,   │
    96→    96→│  core.ts) converts source-specific JSON/XML into the shared             │
    97→    97→│  AcademicPaper interface.                                               │
    98→    98→└──────────────────────────────────┬──────────────────────────────────────┘
    99→    99→                                   │
   100→   100→                                   ▼
   101→   101→┌─────────────────────────────────────────────────────────────────────────┐
   102→   102→│  STEP 4 — DUPLICATE REMOVAL                                             │
   103→   103→│  deduplicatePapers() merges records by DOI first, then by normalized    │
   104→   104→│  title similarity. Merged records keep the richest metadata from all    │
   105→   105→│  sources (longest abstract, highest citation count, union of authors    │
   106→   106→│  and source URLs).                                                      │
   107→   107→└──────────────────────────────────┬──────────────────────────────────────┘
   108→   108→                                   │
   109→   109→                                   ▼
   110→   110→┌─────────────────────────────────────────────────────────────────────────┐
   111→   111→│  STEP 5 — FILTER APPLICATION                                            │
   112→   112→│  applyFilters() removes papers that violate hard constraints: year      │
   113→   113→│  range, min citations, open-access-only, author, publisher, paper type, │
   114→   114→│  include/exclude keywords.                                              │
   115→   115→└──────────────────────────────────┬──────────────────────────────────────┘
   116→   116→                                   │
   117→   117→                                   ▼
   118→   118→┌─────────────────────────────────────────────────────────────────────────┐
   119→   119→│  STEP 6 — INTELLIGENT RANKING                                           │
   120→   120→│  rankPapers() scores each paper 0–100 across 6 dimensions:              │
   121→   121→│   • Semantic relevance to the query keywords (40 pts)                   │
   122→   122→│   • Citation impact — log scale (25 pts)                                │
   123→   123→│   • Recency (15 pts)                                                    │
   124→   124→│   • Publisher / venue reputation (10 pts)                               │
   125→   125→│   • Open-access bonus (5 pts)                                           │
   126→   126→│   • Multi-source discovery bonus (5 pts)                                │
   127→   127→└──────────────────────────────────┬──────────────────────────────────────┘
   128→   128→                                   │
   129→   129→                                   ▼
   130→   130→┌─────────────────────────────────────────────────────────────────────────┐
   131→   131→│  STEP 7 — RESULTS RETURNED                                              │
   132→   132→│  The API returns ranked papers, per-source diagnostics (success/error/  │
   133→   133→│  paper count/duration), the AI-understood query, duplicates-removed     │
   134→   134→│  count, and total search duration.                                      │
   135→   135→└──────────────────────────────────┬──────────────────────────────────────┘
   136→   136→                                   │
   137→   137→                                   ▼
   138→   138→┌─────────────────────────────────────────────────────────────────────────┐
   139→   139→│  STEP 8 — AI INSIGHTS (ON DEMAND)                                       │
   140→   140→│  When a user opens a paper detail page, an async call to               │
   141→   141→│  /api/ai/summarize generates structured insights:                       │
   142→   142→│   • Summary (2–3 sentences)                                             │
   143→   143→│   • Key Contributions (3–5 bullets)                                     │
   144→   144→│   • Advantages (2–4 bullets)                                            │
   145→   145→│   • Limitations (2–4 bullets)                                           │
   146→   146→│   • Future Scope (2–3 bullets)                                          │
   147→   147→│   • Extracted Keywords                                                  │
   148→   148→└──────────────────────────────────┬──────────────────────────────────────┘
   149→   149→                                   │
   150→   150→                                   ▼
   151→   151→┌─────────────────────────────────────────────────────────────────────────┐
   152→   152→│  STEP 9 — PERSIST & RECOMMEND                                           │
   153→   153→│  • Every search is logged to SearchHistory.                             │
   154→   154→│  • Saved papers persist to SavedPaper (with cached AI insights).        │
   155→   155→│  • Citation exports are logged to ExportRecord.                         │
   156→   156→│  • The Profile page can ask the AI for recommended topics based on     │
   157→   157→│    saved papers.                                                        │
   158→   158→└─────────────────────────────────────────────────────────────────────────┘
   159→   159→```

   163→   163→## 4. Tech Stack
   164→   164→
   165→   165→The project is implemented as a **unified full-stack Next.js application** (the original spec proposed a separate React frontend + FastAPI backend, but a unified Next.js app delivers the same functionality with simpler deployment and zero CORS friction).
   166→   166→
   167→   167→### Frontend
   168→   168→- **Next.js 16** (App Router, React Server Components)
   169→   169→- **React 19**
   170→   170→- **TypeScript 5**
   171→   171→- **Tailwind CSS 4** for styling
   172→   172→- **shadcn/ui + Radix UI** for the component library (40+ components)
   173→   173→- **Zustand** for client-side state management
   174→   174→- **lucide-react** for icons
   175→   175→- **sonner** for toast notifications
   176→   176→- **framer-motion** for animations
   177→   177→
   178→   178→### Backend (all inside Next.js API routes)
   179→   179→- **Next.js Route Handlers** (`/app/api/*`) — Node.js runtime
   180→   180→- **Prisma ORM 6** with **SQLite** (file-based DB at `db/custom.db`) for zero-config persistence
   181→   181→- **z-ai-web-dev-sdk** for LLM calls (query understanding, paper summarization, recommendations)
   182→   182→
   183→   183→### External APIs Consumed
   184→   184→- **Semantic Scholar Graph API** — `https://api.semanticscholar.org/graph/v1/paper/search`
   185→   185→- **arXiv Atom API** — `https://export.arxiv.org/api/query`

   188→   188→- **CORE v3 API** — `https://api.core.ac.uk/v3/search/works` (optional, requires API key; gracefully skips)

   272→   272→## 6. Multi-Source Academic API Integration
   273→   273→
   274→   274→Each source has a dedicated adapter in `src/lib/academic/sources/`. All adapters share the same contract: take a query string and limit, return `Promise<AcademicPaper[]>`.
   275→   275→
   276→   276→### 6.1 Semantic Scholar (`semantic-scholar.ts`)
   277→   277→- **Endpoint:** `GET https://api.semanticscholar.org/graph/v1/paper/search`
   278→   278→- **Fields requested:** title, abstract, year, venue, publicationVenue, authors, citationCount, openAccessPdf, isOpenAccess, publicationTypes, journal, externalIds, fieldsOfStudy
   279→   279→- **Sort:** `citationCount:desc`
   280→   280→- **Normalization:** DOI extracted from `externalIds.DOI`; PDF link from `openAccessPdf.url`; keywords from `fieldsOfStudy`; publisher from `publicationVenue.name` → `journal.name` → `venue`.
   281→   281→- **Resilience:** HTTP 429 (rate limit) returns empty array instead of failing the whole search.
   282→   282→
   283→   283→### 6.2 arXiv (`arxiv.ts`)
   284→   284→- **Endpoint:** `GET https://export.arxiv.org/api/query` (Atom XML feed)
   285→   285→- **Query construction:** splits the query into terms and joins them with `AND` for arXiv's field-prefix syntax.
   286→   286→- **Parsing:** custom regex-based Atom XML parser (no XML library dependency) extracts title, summary, published date, DOI, journal_ref, primary_category, authors, and PDF/abstract links.
   287→   287→- **Normalization:** arXiv IDs are extracted from the `id` URL; year parsed from the `published` date; keywords heuristically extracted from title + abstract.
   288→   288→- **Note:** arXiv doesn't return citation counts — they default to `0`. arXiv papers are always marked open-access.
   289→   289→
   290→   290→### 6.3 Crossref (`crossref.ts`)
   291→   291→- **Endpoint:** `GET https://api.crossref.org/works`
   292→   292→- **Fields selected:** DOI, title, author, abstract, published-print/online, issued, created, is-referenced-by-count, publisher, type, link, license, subject, container-title.
   293→   293→- **Sort:** `is-referenced-by-count` (descending).
   294→   294→- **Normalization:** Crossref abstracts are wrapped in `<jats:p>` tags — stripped via regex. Year is picked from the first available date field. PDF link extracted from `link[].content-type === 'application/pdf'`. Open-access determined by Creative Commons / "open access" license URL patterns.
   295→   295→- **Polite pool:** includes `mailto` parameter and User-Agent string for Crossref's polite-data pool.
   296→   296→
   297→   297→### 6.4 PubMed (`pubmed.ts`)
   298→   298→- **Endpoints:** Two-step E-utilities flow:
   299→   299→  1. `GET https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esearch.fcgi` — returns PMIDs matching the query.
   300→   300→  2. `GET https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esummary.fcgi` — fetches article metadata for those PMIDs.
   301→   301→- **Normalization:** title from ESummary, year parsed from `pubdate`, DOI extracted from `articleids` (where `IdType === "doi"`), source URL built from PMID.
   302→   302→- **Limitation:** ESummary doesn't return abstracts — they're set to a placeholder pointing users to the PubMed page.
   303→   303→
   304→   304→### 6.5 CORE (`core.ts`) — optional
   305→   305→- **Endpoint:** `POST https://api.core.ac.uk/v3/search/works`
   306→   306→- **Note:** CORE requires an API key for most usage; the adapter gracefully skips (returns `[]`) on 401/403 without failing the search.
   307→   307→
   308→   308→### 6.6 Orchestrator (`orchestrator.ts`)
   309→   309→The orchestrator:
   310→   310→1. Picks the best search term from the AI-understood query.
   311→   311→2. Spawns all enabled source adapters concurrently with `Promise.all`.
   312→   312→3. Wraps each adapter in a `withTimeout()` (default 12s) so a slow source doesn't block the response.
   313→   313→4. Flattens all results.
   314→   314→5. Deduplicates, filters, ranks, and caps to `finalLimit`.
   315→   315→
   316→   316→Each source result includes a `SourceResult` object: `{ source, papers, success, error?, durationMs }` — surfaced in the UI as a per-source status bar.

   320→   320→## 7. AI Capabilities
   321→   321→
   322→   322→All AI calls go through `src/lib/ai/assistant.ts`, which wraps the **z-ai-web-dev-sdk** with a singleton instance and three primary functions.
   323→   323→
   324→   324→### 7.1 `understandQuery(rawQuery, filters)` → `AIUnderstoodQuery`
   325→   325→
   326→   326→Sends the user's natural-language query + any explicit filters to the LLM with a strict system prompt that forces a JSON response:
   327→   327→
   328→   328→```json
   329→   329→{
   330→   330→  "topic": "the main research topic (concise, 2-6 words)",
   331→   331→  "intent": "1-2 sentence description of what the user is trying to find",
   332→   332→  "keywords": ["core keywords, 3-8 items"],
   333→   333→  "excludeKeywords": ["keywords to exclude, may be empty"],
   334→   334→  "searchTerms": ["1-3 alternative search term strings"],
   335→   335→  "filters": { "yearFrom": ..., "yearTo": ..., "minCitations": ..., ... },
   336→   336→  "reasoning": "1-2 sentences explaining your interpretation"
   337→   337→}
   338→   338→```
   339→   339→
   340→   340→**Resilience:** If the LLM fails or returns malformed JSON, the function falls back to `heuristicUnderstand()` — a deterministic keyword extractor that strips stop words and preserves any user-supplied filters.
   341→   341→
   342→   342→### 7.2 `summarizePaper(title, abstract, userQuery?)` → `PaperInsights`
   343→   343→
   344→   344→Generates a structured AI analysis:
   345→   345→
   346→   346→```json
   347→   347→{
   348→   348→  "summary": "2-3 sentence summary of the paper's main contribution",
   349→   349→  "keyContributions": ["3-5 bullet points"],
   350→   350→  "advantages": ["2-4 strengths"],
   351→   351→  "limitations": ["2-4 weaknesses or constraints"],
   352→   352→  "futureScope": ["2-3 potential future research directions"],
   353→   353→  "keywords": ["5-8 important keywords"]
   354→   354→}
   355→   355→```
   356→   356→
   357→   357→If the LLM fails, falls back to `fallbackInsights()` which surfaces the title + abstract without deep analysis.
   358→   358→
   359→   359→### 7.3 `recommendTopics(savedTitles, currentQuery?)` → `string[]`
   360→   360→
   361→   361→Given the titles of all papers a researcher has saved, suggests 5–8 related research topics they might want to explore next. Used by the Profile page to drive discovery.
   362→   362→
   363→   363→### 7.4 Robust JSON Parsing
   364→   364→The `parseJsonLoose()` helper strips markdown code fences, attempts direct `JSON.parse()`, and falls back to regex extraction of `{...}` or `[...]` blocks. This handles the common LLM failure modes (wrapping JSON in `\`\`\`json` fences, prepending commentary, truncating output).

   368→   368→## 8. The Ranking Engine
   369→   369→
   370→   370→`src/lib/academic/rank.ts` contains two functions:
   371→   371→
   372→   372→### `applyFilters(papers, filters)` — Hard Constraints
   373→   373→Removes papers that violate:
   374→   374→- `yearFrom` / `yearTo` — publication year range
   375→   375→- `minCitations` — minimum citation count
   376→   376→- `openAccessOnly` — must be open access
   377→   377→- `author` — substring match on any author
   378→   378→- `publisher` / `conference` / `journal` — substring match on publisher or venue
   379→   379→- `paperType` — exact match, or `exclude:Review` to drop certain types
   380→   380→- `includeKeywords` — ALL must appear in title/abstract/keywords
   381→   381→- `excludeKeywords` — ANY appearance disqualifies
   382→   382→
   383→   383→### `rankPapers(papers, understood)` — Soft Scoring (0–100)
   384→   384→Each paper is scored across 6 dimensions:
   385→   385→
   386→   386→| Dimension | Max Points | Logic |
   387→   387→|---|---|---|
   388→   388→| **Semantic relevance** | 40 | Title match with topic words (15) + keyword coverage across title/abstract/keywords (15) + title keyword density (10). Exclude keywords incur a -10 penalty each. |
   389→   389→| **Citation impact** | 25 | `min(25, log10(citations + 1) × 10)` — log scale so a 10k-citation paper isn't 100× more valuable than a 100-citation one. |
   390→   390→| **Recency** | 15 | ≤1 year old: 15 · ≤3: 12 · ≤5: 8 · ≤10: 4 · else: 1. Doesn't over-penalize classics. |
   391→   391→| **Publisher reputation** | 10 | +10 if publisher matches a curated list (Nature, Science, IEEE, ACM, Springer, Elsevier, Wiley, Cell, Lancet, NEJM, PNAS). +3 if any venue is known. |
   392→   392→| **Open access bonus** | 5 | +5 if the paper is freely accessible. |
   393→   393→| **Multi-source discovery bonus** | 5 | +5 if the paper appears on ≥3 sources (cross-validated = higher quality), +2 for 2 sources. |
   394→   394→
   395→   395→Final score is clamped to `[0, 100]` and stored on each paper as `relevanceScore`.
   396→   396→

   398→   398→
   399→   399→## 9. Duplicate Detection & Merging
   400→   400→
   401→   401→`src/lib/academic/dedup.ts` performs cross-source deduplication in two passes:
   402→   402→
   403→   403→1. **DOI match (primary)** — papers with the same DOI (case-insensitive, trimmed) are merged.
   404→   404→2. **Title match (fallback)** — papers without DOIs are matched by `titleKey()` — a normalized lowercase title with punctuation stripped. Only titles longer than 10 chars are eligible (avoids spurious merges on short generic titles).
   405→   405→
   406→   406→### Merge Strategy (`mergeInto`)
   407→   407→When two records are merged, the surviving record keeps the **richest** version of every field:
   408→   408→
   409→   409→- **Sources** — union (e.g. `["Semantic Scholar", "arXiv"]`)
   410→   410→- **Source URLs** — union, deduped by URL
   411→   411→- **Abstract** — the longer one wins
   412→   412→- **Citation count** — the larger one wins
   413→   413→- **Missing fields** — filled from the source record (DOI, PDF link, year, publisher, venue, paper type, open-access flag)
   414→   414→- **Authors** — union, deduped by normalized name
   415→   415→- **Keywords** — union, deduped case-insensitively
   416→   416→
   417→   417→This is what lets a single paper appear in the UI as *"found on Semantic Scholar + arXiv + Crossref"* — its metadata is the superset of all three.

   589→   589→## 13. Citation Export
   590→   590→
   591→   591→`src/lib/citation.ts` implements four citation formatters — all pure functions, no external libraries:
   592→   592→
   593→   593→### APA (7th edition)
   594→   594→- Authors: `Last, F. M., & Last, F. M.` (up to 20; uses `...` ellipsis for 21+)
   595→   595→- Format: `Author(s) (Year). Title. Venue. https://doi.org/...`
   596→   596→
   597→   597→### MLA (9th edition)
   598→   598→- Authors: `Last, First` for one; `Last, First, et al.` for multiple
   599→   599→- Format: `Authors. "Title." Venue, Year. doi: ...`
   600→   600→
   601→   601→### BibTeX
   602→   602→- Generates a `@article{...}` entry with `title`, `author` (joined with ` and `), `year`, `journal`, `doi`, `url`.
   603→   603→- Bib key auto-generated from first author's last name + year + first title word.
   604→   604→
   605→   605→### Chicago (17th edition)
   606→   606→- Authors: `Last, First` for one; `Last, First, et al.` for multiple
   607→   607→- Format: `Authors. "Title." Venue, Year. https://doi.org/...`
   608→   608→
   609→   609→All formats are surfaced through the `/api/citation` endpoint and the citation panel on the Details page.

   681→   681→## 17. Implementation Highlights
   682→   682→
   683→   683→### Resilience Patterns
   684→   684→- **Per-source timeouts** (12s) — a slow source doesn't block the response.
   685→   685→- **Per-source error isolation** — if one source fails, others still return results; the failure is surfaced in the UI as a red badge with the error message.
   686→   686→- **Rate-limit handling** — Semantic Scholar's HTTP 429 returns `[]` instead of throwing.
   687→   687→- **AI fallbacks** — if the LLM fails to return parseable JSON for query understanding, a heuristic keyword extractor takes over. If summarization fails, a placeholder insight is returned.
   688→   688→- **Fire-and-forget persistence** — search history and export records are written asynchronously without blocking the API response.
   689→   689→
   690→   690→### Type Safety
   691→   691→- All API contracts are typed via `src/lib/academic/types.ts` (`AcademicPaper`, `AIUnderstoodQuery`, `SearchFilters`, `SearchResult`, `SourceResult`, `PaperInsights`).
   692→   692→- The Prisma schema generates typed client methods — no raw SQL anywhere.
   693→   693→
   694→   694→### State Management
   695→   695→- **Zustand** for client state — single store with slices for navigation, search, results, compare, saved, and theme.
   696→   696→- **No React Context boilerplate** — components subscribe directly to store slices via `useAppStore((s) => s.someField)` for selective re-rendering.
   697→   697→
   698→   698→### Performance
   699→   699→- Parallel source fetching with `Promise.all`.
   700→   700→- AI insights are generated lazily (only when a paper is opened) and cached on the paper object — re-opening doesn't re-call the LLM.
   701→   701→- Prisma client is singleton-cached on `globalThis` to avoid connection pool exhaustion in dev.
   702→   702→
   703→   703→### UX Details
   704→   704→- **Color-coded source badges**: Semantic Scholar (emerald), arXiv (red), Crossref (orange), PubMed (blue), CORE (purple).
   705→   705→- **Dark/light theme toggle** in the header.
   706→   706→- **Keyboard shortcut** ⌘+↵ to submit the hero search.
   707→   707→- **Toast notifications** for save/remove/cite actions.
   708→   708→- **Skeleton loaders** during search and AI generation.
   709→   709→- **Responsive layout** — filters collapse to a drawer on mobile, comparison table scrolls horizontally.
